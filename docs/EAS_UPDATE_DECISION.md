# EAS Update decision — over-the-air JS releases for the iOS app

*2026-09-14. Prompted by the Tree Health duplicate-person change (PR #18): a
JavaScript-only fix that, under today's release path, still costs an Xcode
build on the laptop plus an App Store review before any phone or iPad sees
it. This is a recommendation with its reasoning shown, not a verdict.*

*Sourcing note: `expo.dev` and `docs.expo.dev` are blocked from the
environment this was written in, so the Expo-specific details below (CLI
flags, runtime-version policies, plan limits) come from prior knowledge of
EAS Update and must be re-verified against the SDK 57 docs
(`https://docs.expo.dev/versions/v57.0.0/`) before setup. The repo facts
are verified.*

## Where releases stand today

Verified from the repo:

- The iOS app is a native App Store build: `com.witnesslives.witness`,
  version `1.8.0`, build `16`, Expo SDK `~57.0.1`, React Native `0.86.0`.
- **No over-the-air path exists.** `expo-updates` is not in
  `apps/mobile/package.json`, there is no `eas.json`, and `app.json` has no
  `runtimeVersion` or `updates` config. The `ios/` project is generated by
  prebuild and built with Xcode on Rufus's Mac (the `verify` skill's
  `xcodebuild` / `devicectl` path).
- The web app has its own, separate release path (Vercel, per
  `apps/mobile/AGENTS.md`) and is unaffected by any of this.

Consequence: **every** change to the phone app, native or not, is a
laptop session plus an Apple review cycle. The duplicate-person check is
a pure `packages/core` + `src/lib` change — nothing native moved — and it
still pays that full price.

## What EAS Update would change

EAS Update lets a binary that already carries `expo-updates` download a
new JavaScript bundle (plus bundled assets) from Expo's CDN and run it on
a later launch. The App Store binary stays exactly as reviewed; only the
JS layer moves.

**Eligible for OTA** (the large majority of Witness's day-to-day changes):

- Anything under `apps/mobile/src/` and `packages/core/` — Tree Health
  checks, query library, screens, copy, the curiosities cache, deep-link
  handling, the GEDCOM parser.
- Assets the JS bundle references (images required from code).

**Still a binary release** (rule of thumb: if `npx expo prebuild` output
would change, it's a binary):

- Adding or upgrading a native module (anything that touches the Pods —
  maps, purchases, file system, DOM components).
- `app.json` native config: permissions strings, bundle identifier, URL
  schemes, icons/splash, associated domains.
- Expo SDK or React Native upgrades.

The runtime-version mechanism is what keeps this safe: each binary carries
a **runtime version**, and an update only applies to binaries whose runtime
version matches. The `fingerprint` policy (Expo hashes the native project
and uses that as the version) is the right default for a solo developer —
it makes the "is this OTA-safe?" question automatic instead of a judgment
call. The `appVersion` policy (runtime version = `1.8.0`) is simpler but
relies on remembering to bump the version whenever native code changes.

## The sequencing gotcha

**Setting this up delivers nothing until one more App Store release ships.**
The update URL, channel, and runtime version are baked into the binary at
build time. Build `16` on everyone's phones today knows nothing about EAS
Update and can never receive one. So the first benefit arrives with the
*second* release after setup:

1. Release N (binary, App Store): carries `expo-updates` + config. Ships
   through the normal Xcode → App Store Connect → review path.
2. Release N+1 onward, for JS-only changes: `eas update` from a terminal,
   no Xcode, no review. Reaches devices on their next-next launch (see
   below).

This is why it should *not* be rushed into this week's deploy: the
duplicate-person check ships fastest as a plain `1.8.1` binary the way
releases ship today. EAS Update is an investment in the release *after*.

## Cost and effort

- **Effort:** roughly half a day of setup, then one binary release to
  carry it. Concretely: `npx expo install expo-updates`, `eas init` /
  `eas update:configure` (creates the EAS project and writes
  `runtimeVersion` + `updates.url` into `app.json`), pick the runtime-version
  policy, define a `production` channel and a `preview` channel, rebuild
  and ship the binary. EAS Build is **not** required — locally built Xcode
  binaries work, as long as the channel is configured in the build
  (verify the exact SDK 57 mechanism for setting the channel on a non-EAS
  build; historically the `expo-updates` config plugin's `requestHeaders`
  `expo-channel-name`).
- **Money:** EAS has a free plan that includes an EAS Update monthly-active-
  user allowance (historically 1,000 MAU; verify current numbers on
  `expo.dev/pricing`). At beta scale that is likely free. The paid
  Production plan (historically ~$99/month) raises the allowance and adds
  build minutes Witness doesn't need. Budget line: probably $0 now, and the
  trigger to pay is real user growth — a good problem.
- **Apple policy:** App Store Review Guideline 3.3.1(B) permits downloaded
  interpreted code (which is what a JS bundle is) provided it does not
  change the app's primary purpose, create a store within the app, or
  bypass review of features. Expo OTA updates are widely used within this;
  the discipline is *don't ship a feature via OTA that you'd be nervous
  submitting for review*. Verify the current guideline text.

## Two behaviours worth knowing before relying on it

1. **The two-launch delay.** By default `expo-updates` checks for a new
   bundle on launch, downloads it in the background, and applies it on the
   *next* launch. So a user opens the app (download), closes it, opens it
   again (new code). Acceptable for tree-health fixes; if a change ever
   needs to land immediately, the app can call
   `Updates.fetchUpdateAsync()` then `Updates.reloadAsync()` — a small
   "an update is ready" affordance, not free.
2. **An OTA is a broadcast.** A JS crash pushed to `production` reaches
   every matching device at once. Mitigations, all cheap: keep the existing
   gates (`npx tsc --noEmit`, the core test suite, a web export) as a
   required pre-`eas update` checklist; push to the `preview` channel first
   and install that channel on Rufus's own phone and iPad — which is exactly
   the "update our devices without the laptop" use case that started this
   note; and know that `eas update` supports rolling back to a previous
   update if one goes wrong.

## What does *not* change

- The web deploy recipe in `AGENTS.md` (Vercel) — EAS Update is native-only.
- The `verify` skill and simulator workflow.
- RevenueCat / Superwall entitlements, Supabase, deep links.
- Xcode remains the path for binary releases; EAS Build stays optional.

## Recommendation

**Do it, sequenced after the next binary release.**

- The change that prompted this note (PR #18) is JS-only and is the exact
  shape of change Witness ships most often. Under the current path each one
  costs a laptop session and a review cycle; under EAS Update each one is a
  terminal command from anywhere with the code checked out.
- The cost is low (likely $0 at current scale, ~half a day once) and the
  safety model — runtime-version gating plus a preview channel on Rufus's
  own devices — is stronger than "hope the App Store build was fine".
- But it is not a shortcut for *this* release: ship `1.8.1` the usual way,
  then make `1.9.0` the binary that carries `expo-updates`.

**Concrete next step:** when the next binary release is being planned,
spend the half day: install `expo-updates`, configure the `fingerprint`
runtime-version policy and `production` / `preview` channels, confirm the
channel mechanism for locally built binaries against the SDK 57 docs,
build and ship. Then verify the loop end to end by pushing a trivial copy
change to `preview` and watching it land on Rufus's iPad on the second
launch. Only after that, promote the practice to `production`.
